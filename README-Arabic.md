# Advertising Campaign & Broadcast Monitoring Suite

## المزايا
نظام ويب لإدارة العملاء والقنوات والبرامج والحملات والمواد الإعلانية وجدولة البث وسجلات التنفيذ. مقارنة المخطط بالفعلي، وتصنيف القادم/المفقود/المتأخر/المطابق، وتصدير CSV. أدوار viewer/operator/manager/admin.

## التشغيل محليًا
1. ثبّت Node.js 20+ وPostgreSQL.
2. أنشئ قاعدة `advertising_broadcast` ثم انسخ `.env.example` إلى `.env` واضبط القيم. **Node لا يقرأ .env تلقائيًا**؛ صدّر المتغيرات في بيئة التشغيل أو استخدم مدير أسرار.
3. نفذ `npm install` ثم `npm start`.
4. افتح `http://localhost:3000`، وسجّل دخولك ببيانات ADMIN_USER وADMIN_PASSWORD. يتم إنشاء الجداول والحساب الأول عند التشغيل الأول.

## نشر Render بدون Docker
1. ارفع ملفات المشروع إلى GitHub.
2. من Render اختر New > Blueprint واربط المستودع؛ سيقرأ `render.yaml`.
3. أدخل ADMIN_USER وADMIN_PASSWORD في واجهة Render؛ واترك JWT_SECRET يولد آليًا، وDATABASE_URL يتصل بقاعدة Render.
4. بعد نجاح النشر افتح `https://YOUR-SERVICE.onrender.com/api/health`، ثم افتح الصفحة الرئيسية وسجل الدخول.
5. خطط Render المجانية وحدودها قد تتغير، وقواعد البيانات المجانية قد تكون مؤقتة؛ تحقق من شروط الخدمة والنسخ الاحتياطي قبل بيانات الإنتاج.

## الاستخدام
ابدأ بإضافة عميل وقناة وبرنامج وحملة ومادة إعلانية، ثم أنشئ Spot بموعد planned_at. عند حدوث البث أضف Airing يتضمن spot_id وactual_at ورابط الدليل. افتح مراقبة البث لعرض المقارنة وتصدير CSV. التوقيت مخزن UTC/ISO؛ استخدم صيغة وقت ISO مع المنطقة الزمنية لضمان دقة المقارنة.

## بناء EXE
على Windows ثبّت Node.js ثم نفذ `npm install` و `npm run build:windows`. سيظهر المثبت داخل `dist/`. افتح التطبيق، ومن تبويب الاتصال ضع عنوان Render HTTPS. **لم يُبنَ ملف EXE داخل هذه الحزمة.**

## بناء APK
ثبّت Android Studio وJava JDK وAndroid SDK وNode.js. نفذ `npm install` ثم `npm run android:add` ثم `npm run android:sync` وافتح `android/` في Android Studio وابنِ APK. هذه حاوية WebView، وليست تطبيقًا .NET MAUI. عند تشغيل التطبيق ضع عنوان Render من تبويب الاتصال. **لم يُبنَ APK داخل هذه الحزمة.**

## ملاحظات وحدود
- هذه نسخة MVP بمصدر فعلي، وليست منصة إنتاج مختبرة بالكامل.
- مراقبة البث مبنية على تسجيلات يدوية أو API؛ لا تتضمن التقاط بث مباشر أو تعرفًا صوتيًا/مرئيًا.
- الواجهة تعتمد حقول معرفات رقمية؛ لا توجد قوائم اختيار مترابطة بعد.
- لا يوجد رفع ملفات أو فوترة أو تصدير PDF أو اختبارات شاملة بعد.
- يجب إضافة rate limiting وaudit log وCSP ونسخ احتياطي وسياسات CORS وتحقق متقدم قبل الإنتاج.
- تطبيق سطح المكتب يعمل بواجهة محلية تتصل بـ API عن بعد، تم تفعيل CORS لأصول تطبيقات الأجهزة وlocalhost؛ ينبغي تضييق السياسة وتحديد PUBLIC_ORIGIN عند الإنتاج. لتسهيل نسخ الأجهزة، يُفضّل ضبط Electron وCapacitor لتحميل رابط Render مباشرة مع قيود الملاحة المناسبة.


## إضافة أكتوبر 2026: المستخدمون واختبارات التطبيقات
- الحساب الأول يُنشأ عند بدء تشغيل قاعدة بيانات جديدة باستخدام ADMIN_USER و ADMIN_PASSWORD.
- المسؤول يضيف مستخدمين بأدوار viewer / operator / manager ويعطل أو يفعل حساباتهم من شاشة المستخدمين. منع إنشاء مسؤول ثانٍ من الواجهة/API؛ تظل بيانات المسؤول الأساسي محمية.
- قائمة اختبار التطبيقات تنشئ جلسات لموقع أو API أو EXE أو APK، ثم تسجل حالات Passed/Failed/Blocked وتعرض تقريرًا قابلًا للقراءة.
- صفحة تحليل المراقبة تستخرج مؤشرات وتوصيات مبنية على قواعد من بيانات البث. **ليست تكاملًا فعليًا مع نموذج ذكاء اصطناعي** ولا تتعرف على الفيديو أو الصوت.
- التشغيل الآلي لاختبارات المتصفح يحتاج Playwright في عامل اختبار منفصل، واختبارات APK تحتاج Android emulator/Appium، واختبارات EXE تحتاج Windows runner؛ لا ينفذ Render Linux ملفات EXE أو APK مباشرة.
- **أمان الإنتاج:** يتطلب تعطيل الحساب إبطال الجلسات القائمة أيضًا (إصدار توكن/فحص قاعدة البيانات عند كل طلب)؛ في النسخة الحالية تظل التوكنات الصادرة سابقًا صالحة حتى انتهاء 8 ساعات. لا تعتبرها جاهزة لبيانات إنتاج حساسة.
